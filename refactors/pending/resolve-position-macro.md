# resolve-position-macro: the derive surface

The derive walks children and, when the walk stops, produces a `ResolvedNode`. Configuring a site is answering two questions: how to build the child's `Parent` when descending, and how to build this type's `ResolvedNode` when no child contains the position.

This doc is the surface. Change 1 and Change 2 rename the two attributes whose names do not match that split.

## Container: `#[resolve_position(...)]`

```rust
// from crates/resolve_position_macros/src/resolve_position_macro.rs
struct ResolvePositionArgs {
    parent_type: Option<syn::Type>,
    resolved_node: syn::Type,
    self_type_generics: Option<SelfTypeGenerics>,
    on_unmatched_span: Option<syn::Ident>,
}

struct SelfTypePin {
    args: syn::AngleBracketedGenericArguments,
    parent_type: syn::Type,
}
```

`resolved_node` is this type's `ResolvePosition::ResolvedNode`. Required.

`parent_type` is this type's `ResolvePosition::Parent`. Required when `self_type_generics` is omitted. Forbidden when `self_type_generics` is present: each pin carries its own.

`self_type_generics` is a list of pins `[ (<A, B>, ParentTy), ... ]`. Omitted: one impl over the type's own generics (`split_for_impl`). Present: one impl per pin, `ty_generics = pin.args`, `parent_type = pin.parent_type`, no impl generics. One pin may use `on_unmatched_span = struct_name` (the default). Two or more pins require `on_unmatched_span = from_path`. An empty list is a compile error. Container `parent_type` next to a list is a compile error.

```rust
// from crates/isograph_parser/src/chunk.rs
#[resolve_position(parent_type = ChunkParent<'a>, resolved_node = IsographResolutionNode<'a>)]
pub struct Chunk {
```

```rust
// from crates/isograph_parser/src/chunk.rs
#[resolve_position(
    resolved_node = IsographResolutionNode<'a>,
    on_unmatched_span = from_path,
    self_type_generics = [
        (<IsoLiteralItem, UnparsedChunkItems>, IsoLiteralParsePath<'a>),
    ]
)]
pub struct Slot<T, E> {
```

`on_unmatched_span` is a struct attribute. Enums reject it: they have no unmatched arm. Values:

- omitted or `struct_name`: `return Self::ResolvedNode::#struct_name(self.path(parent).to());`
- `from_path`: `return self.path(parent).to();` plus a `From<Path<&Self, Parent>> for ResolvedNode` bound

A transparent field suppresses the unmatched arm: that field always answers.

```rust
// generated by resolve_position_macros/src/resolve_position_macro.rs
                return Self::ResolvedNode::#struct_name(self.path(parent).to());
```

```rust
// generated by resolve_position_macros/src/resolve_position_macro.rs
                return self.path(parent).to();
```

`on_unmatched_span` builds `ResolvedNode`. It does not build `Parent`.

## Struct fields: whether to walk, and how to build the child's `Parent`

Unmarked: skipped.

`#[resolve_field]` is the opt-in. The field type must be `WithSpan<T>`, `WithLocation<T>`, `WithEmbeddedLocation<T>`, or `GraphQLTypeAnnotation<T>`, or `Vec` / `Option` / `NonEmpty` of those. The walk is a span check then `item.resolve(new_parent, position)`. `Vec` / `Option` / `NonEmpty` iterate, then the inner check.

How `new_parent` is built:

```rust
// from crates/resolve_position_macros/src/resolve_position_macro.rs
enum ParentConstruction {
    ContainerPath,
    EnumVariant(syn::Ident),
    FromContainer,
    Transparent,
}
```

```rust
// generated by resolve_position_macros/src/resolve_position_macro.rs
        ParentConstruction::ContainerPath => quote!(self.path(parent)),
        ParentConstruction::EnumVariant(variant) => quote!(
            <#inner_type as ::resolve_position::ResolvePosition>::Parent::#variant(self.path(parent).into())
        ),
        ParentConstruction::FromContainer => {
            quote!(::std::convert::From::from(self.path(parent)))
        }
```

Bare `#[resolve_field]`: `ContainerPath`. The child's `Parent` is the container's path. `Chunk.trailing_separator` is this. `Slot.item` is this. `ArgumentList`'s vec is this.

`#[resolve_field]` + `#[parent_variant(V)]`: `EnumVariant`. The child's `Parent` is an enum. The container path is wrapped in `V`. `Chunk.contents` is `Chunk`. `UnparsedChunkItems`'s vec is `Unparsed`. `NamedArgument.name` is `NamedArgument`.

```rust
// from crates/isograph_parser/src/chunk.rs
pub struct Chunk {
    #[resolve_field]
    #[parent_variant(Chunk)]
    contents: NonEmpty<WithSpan<ChunkContentItem>>,
    #[resolve_field]
    trailing_separator: Option<WithSpan<ChunkSeparator>>,
}
```

`#[resolve_field]` + `#[from_container_parent]`: `FromContainer`. The child's `Parent` is `From` of the container path. parse-arguments.md is the first caller on `Slot.extra_tokens`. One field, a different variant per pin: `parent_variant` cannot name them.

`#[resolve_field(transparent)]`: no span check, `parent` passed through, no path segment, no unmatched arm on the container. Cannot combine with `parent_variant` or `from_container_parent`. Cannot sit on a `WithSpan<T>` field.

`parent_variant` or `from_container_parent` without `resolve_field` is a compile error. Combining `parent_variant` and `from_container_parent` is a compile error.

## Enum payloads: always walk, and how to build the child's `Parent`

A variant has one unnamed field. Anything else is a compile error. `#[resolve_field]` on a payload is a compile error: the payload always resolves.

Unmarked: `inner.resolve(parent, position)`. The payload's `Parent` equals the enum's `Parent`. `ChunkContentItem::NonBracket` is this. `NonConstantValue::Variable` is this.

`#[parent_variant(V)]`: wrap the incoming `parent`, not a container path. The enum is not a path segment.

```rust
// generated by resolve_position_macros/src/resolve_position_macro.rs
                    #enum_name::#variant_name(inner) => inner.resolve(
                        <#payload_type as ::resolve_position::ResolvePosition>::Parent::#parent_variant(parent.into()),
                        position,
                    )
```

`#[from_container_parent]`: `From::from(parent)`. Same incoming `parent`, not a container path.

```rust
// generated by resolve_position_macros/src/resolve_position_macro.rs
                    #enum_name::#variant_name(inner) => inner.resolve(
                        ::std::convert::From::from(parent),
                        position,
                    )
```

`transparent` on a payload is a compile error: unmarked already forwards `parent`. Combining `parent_variant` and `from_container_parent` is a compile error.

Struct `parent_variant` / `from_container_parent` start from `self.path(parent)`. Enum `parent_variant` / `from_container_parent` start from the incoming `parent`. The attribute names do not say that. The operations are the same: wrap in `V`, or `From`.

## Names

`parent_type`, `resolved_node`, `resolve_field`, `parent_variant`, `on_unmatched_span`, `struct_name`, `from_path`, and `transparent` match the mechanism.

`self_type_generics` does not. It is a list of pins. generic-slot.md already calls each entry a pin. The name is leftover from when the argument was only type arguments.

`from_container_parent` does not. On a struct it converts the container path. On an enum there is no container path; it converts the incoming `parent`. The old name `parent_from` (parent-variant-attribute.md, before the rename to `from_container_parent`) names the operation: `Parent` by `From`. It pairs with `parent_variant` (`Parent` by variant) and does not collide with `from_path` (`ResolvedNode` by `From` of the path).

Proposed surface:

```rust
#[resolve_position(
    parent_type = ChunkParent<'a>,
    resolved_node = IsographResolutionNode<'a>,
)]
```

```rust
#[resolve_position(
    resolved_node = IsographResolutionNode<'a>,
    on_unmatched_span = from_path,
    pins = [
        (<IsoLiteralItem, UnparsedChunkItems>, IsoLiteralParsePath<'a>),
    ]
)]
```

```rust
    #[resolve_field]
    #[parent_variant(Chunk)]
    contents: NonEmpty<WithSpan<ChunkContentItem>>,
    #[resolve_field]
    trailing_separator: Option<WithSpan<ChunkSeparator>>,
    #[resolve_field]
    #[parent_from]
    extra_tokens: Option<WithSpan<E>>,
```

```rust
    Unparsed(#[parent_from] Unparsed),
```

`on_unmatched_span = struct_name` stays. It names the `ResolvedNode` variant after the struct. That is what the emission does.

## Change 1: `self_type_generics` is `pins`

Origin: `ResolvePositionArgs`, `SelfTypeGenerics` parse, error strings, the derive `attributes(...)` list does not name this (it is an argument of `resolve_position`). Delta: the argument is `pins`. `<A, B>` without the pin tuple stays a parse error.

```rust
// from crates/resolve_position_macros/src/resolve_position_macro.rs
struct ResolvePositionArgs {
    parent_type: Option<syn::Type>,
    resolved_node: syn::Type,
    pins: Option<SelfTypeGenerics>,
    on_unmatched_span: Option<syn::Ident>,
}
```

Error strings that say `self_type_generics` say `pins`. Empty list: `` `pins` must contain at least one pin ``. Container `parent_type` with a list: `` `parent_type` is on each pin when `pins` is present ``. Two or more pins still require `on_unmatched_span = from_path`.

Live sites: `Slot` and `Singleton` in `crates/isograph_parser/src/chunk.rs`. Tests: `crates/resolve_position_macros/tests/self_type_generics_pins.rs`, `from_container_parent_field.rs`. Pending docs that write the list: parse-arguments.md, parsing-standards.md.

```rust
// from crates/isograph_parser/src/chunk.rs
    pins = [
        (<IsoLiteralItem, UnparsedChunkItems>, IsoLiteralParsePath<'a>),
    ]
```

Before: `self_type_generics = [ ... ]`.

`cargo test -p resolve_position_macros` and `cargo test -p isograph_parser` pass.

## Change 2: `from_container_parent` is `parent_from`

Origin: the derive `attributes(...)` list, `collect_field_attributes`, `parse_from_container_parent`, error strings, enum-payload emission, struct-field `FromContainer`. Delta: the attribute is `parent_from`. Error strings that name `from_container_parent` name `parent_from`. Combining with `parent_variant` still errors.
