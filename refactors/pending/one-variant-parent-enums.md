# One-variant parent enums

Some parent enums have exactly one variant: raw-items.md has `BracketItemParent { MatchedBrackets(..) }` and `BracketTokenParent { Bracketed(..) }`, and iso1 has `ClientObjectSelectableNameWrapperParent { ClientPointerDeclaration(..) }` and `VariableNameWrapperParentType { VariableDeclarationInner(..) }`. This doc records why the derive forces them and the two macro changes that would remove the need. Neither change is scheduled: raw-items.md lands against the macro as it is, and this doc exists so the mechanism is on file if the boilerplate grows.

## Why the derive forces them

The derive's field emission has exactly one shape. For a `#[resolve_field]` field it generates, from resolve_position_macro.rs:

```rust
// generated by resolve_position_macros/src/resolve_position_macro.rs
if self.field.location.contains(position) {
    let new_parent = <Child as ::resolve_position::ResolvePosition>::Parent::Container(self.path(parent).into());
    return self.field.item.resolve(new_parent, position);
}
```

`Container` is the deriving type's own name. The emission is the derive's calling convention: a proc macro sees only the tokens of the item it is attached to, so at the field site it knows the container's name and nothing about the child's parent type — not whether it is an enum, not what variants it has. Naming a variant after the container is what lets the generated code compile without that knowledge; the compiler then checks that the variant exists.

When a child appears in several containers, the variant carries information — it says which container the resolution path went through. When a child appears in exactly one container, the natural parent type would be the container's path itself (`type ChildParent<'a> = ContainerPath<'a>`), but the emission still writes `Parent::Container(..)`, and a path alias has no variants. So the parent must be an enum with one variant whose only job is to satisfy the emission. The variant carries no information; it is the derive's calling convention made visible.

The alternative to the one-variant enum under today's macro is a hand-written impl, which raw-items.md had and removed: iso1 hand-writes only where a derive physically cannot attach (`Selection` is a type alias of the shared generic enum `SelectionType`), not to escape the emission shape.

## Change A: route the parent through `From`

The emission stops naming a variant and converts instead:

```rust
// generated by resolve_position_macros/src/resolve_position_macro.rs, after change A
if self.field.location.contains(position) {
    let new_parent: <Child as ::resolve_position::ResolvePosition>::Parent<'_> =
        self.path(parent).into();
    return self.field.item.resolve(new_parent, position);
}
```

For a single-container child, `ChildParent` becomes the alias `ContainerPath<'a>` and the `.into()` is the reflexive `From` — the one-variant enum disappears with zero replacement code. For a multi-container child, every container needs an impl the variant used to provide for free:

```rust
impl<'a> From<ContainerPath<'a>> for ChildParent<'a> {
    fn from(path: ContainerPath<'a>) -> Self {
        ChildParent::Container(path)
    }
}
```

The costs: one `From` impl per (child, container) pair across the whole tree, which in raw-items.md means impls for every variant of `MatchedBracketsParent` and friends, so the boilerplate moves rather than shrinking unless most children are single-container; the boxing today's `.into()` does for `Box` payloads moves inside those impls; and two containers of one child with the same path type would make the `From` impls overlap, which the named variant can never do. refactors/past/resolve-position-parent-conversion.md explored this direction and is parked with no consumer.

## Change B: a field attribute that skips the variant

The emission keeps its shape, and a flag on the field says the child's parent is the container's path itself:

```rust
#[resolve_position(parent_type = MatchedBracketsParent<'a>, resolved_node = ResolvedBracketNode<'a>)]
pub struct MatchedBrackets(#[resolve_field(parent_is_path)] pub Vec<WithSpan<BracketItem>>);
```

```rust
// generated by resolve_position_macros/src/resolve_position_macro.rs, after change B
if item.location.contains(position) {
    let new_parent = self.path(parent);
    return item.item.resolve(new_parent, position);
}
```

With `type BracketItemParent<'a> = MatchedBracketsPath<'a>;` the types line up with no conversion at all: `path` already returns the container's path. Multi-container children keep the named-variant emission unchanged, so nothing else in the tree moves. The costs: a second emission mode in the macro and an attribute the reader must know; and the flag states a fact the macro cannot check — if the child's parent type is not the container's path, the error surfaces as a type mismatch inside generated code rather than as a missing variant.

## What this buys

In raw-items.md, change B would delete `BracketItemParent` and `BracketTokenParent` as enums and one destructuring layer at every consumer (`let BracketItemParent::MatchedBrackets(level) = token.parent;` becomes a direct field access). Against that, the one-variant enum is future-proof in the same way iso1 relies on: when a second container appears, it grows a variant and every consumer match gets a new arm to write, whereas an alias parent changes type and every consumer signature changes shape.

## Status

Nothing here is scheduled. raw-items.md requires no macro changes and pays the two one-variant enums as written. If a change is picked up later, it needs its own pending doc with the macro diff and every call-site change written out.
