# GraphQL protocol: the normalization AST

Status: not actively worked.

The normalization AST is the first real runtime artifact. It replaces the `export default {};` stub that `refactors/pending/artifact-set-and-types.md` change 3 writes at `<Entity>/<selectable>/normalization_ast.ts` for every `entrypoint` literal. It is built from the same `OperationDocument` that `print_operation_document` prints (`query-generation.md` in this directory), so the query text and the AST match by construction: every field the query selects is one AST node, under the alias the query gives it, and every `... on T` in the query is one conditional AST node.

v1 has no runtime cache work. The artifacts are generated and asserted on by tests; `refactors/pending/runtime/pico-runtime.md` is the later consumer.

Upstream references are the checkout at `/Users/rbalicki/code/isograph` (commit `79e2a3c0`).

`entrypoint.ts` is unchanged from artifact-set-and-types.md decision 4 (b): it imports `./normalization_ast` and exports it as `normalizationAst`. What changes is the imported module's default export, from `{}` to the array above.

The array is declared with the type `NormalizationAst`, so TypeScript checks every node against the types below and keeps each `kind` a literal type (`"Scalar"`, not `string`). The module imports only that type; `import type` is erased, so the module has no runtime import.

What the AST shows:

- The nodes appear in the order of the query's lines, including the `id` and `__typename` the operation document adds and the `node` field of a `Node` fetch.
- `responseKey` is the exact alias the query text prints before `:`. The normalizer reads `response[responseKey]` and never recomputes an alias from `fieldName` and `arguments`.
- `fieldName` and `arguments` remain because the store key resolves variables to their values (upstream `getParentRecordKey`, `isograph/libs/isograph-react/src/core/cache.ts:454-521`), which the response key does not.
- `... on Pet { .. }` is a `Conditional` node whose condition is "the field `__typename` of this response object equals `"Pet"`".

`entrypoint Query.PetDetailRoute`'s `pet____id___v_id: pet(id: $id)` is `{ kind: "Linked", responseKey: "pet____id___v_id", fieldName: "pet", arguments: [["id", { kind: "Variable", name: "id" }]], concreteType: "Pet", selections: [..] }`: `Pet` is an object type, so its record's type is known without `__typename`.

A query whose operation document fails fails its AST too; there is no AST without query text and no query text without an AST.

## The artifact's TypeScript type

```ts
// from libs/isograph-runtime/src/artifacts.ts
/** The default export of a `normalization_ast.ts` artifact. */
export type NormalizationAst = NormalizationSelectionSet;

export type NormalizationSelectionSet = ReadonlyArray<NormalizationSelection>;

export type NormalizationSelection =
  | NormalizationScalarField
  | NormalizationLinkedField
  | NormalizationConditional;

export type NormalizationScalarField = {
  readonly kind: "Scalar";
  /** The alias the query text gives this field: the key of its value in the response. */
  readonly responseKey: string;
  readonly fieldName: string;
  readonly arguments: Arguments | null;
};

export type NormalizationLinkedField = {
  readonly kind: "Linked";
  readonly responseKey: string;
  readonly fieldName: string;
  readonly arguments: Arguments | null;
  /** The target type when it is an object type; `null` when it is an interface or union. */
  readonly concreteType: string | null;
  readonly selections: NormalizationSelectionSet;
};

/** Selections normalized onto the parent's record when `condition` holds. */
export type NormalizationConditional = {
  readonly kind: "Conditional";
  readonly condition: NormalizationCondition;
  readonly selections: NormalizationSelectionSet;
};

export type NormalizationCondition =
  | {
      readonly kind: "FieldEquals";
      /** A field selected earlier in the same selection set. */
      readonly responseKey: string;
      readonly value: string;
    }
  | {
      readonly kind: "VariableEquals";
      readonly name: string;
      readonly value: boolean;
    };

export type Arguments = ReadonlyArray<Argument>;
export type Argument = readonly [string, ArgumentValue];

export type ArgumentValue =
  | { readonly kind: "Variable"; readonly name: string }
  | { readonly kind: "Literal"; readonly value: number | boolean | null }
  | { readonly kind: "String"; readonly value: string }
  | { readonly kind: "Object"; readonly value: Arguments };
```

`NormalizationAst` is the name the artifact imports; `NormalizationSelectionSet` is the type of a nested `selections`. They are one type because i2 drops upstream's wrapper object (deltas below). Upstream's `NormalizationAst` is the wrapper and its nested type is `NormalizationAstNodes` (`isograph/libs/isograph-react/src/core/entrypoint.ts:127-132`).

### How the artifact is constrained

Held, upstream's shape: a type import, a `const` declared with the type, and a default export of the binding:

```ts
import type { NormalizationAst } from "@isograph/runtime";
const normalizationAst: NormalizationAst = [..];
export default normalizationAst;
```

Upstream's generated line is `import type {NormalizationAst} from '@isograph/react';` (`isograph/demos/pet-demo/src/components/__isograph/Mutation/SetTagline/normalization_ast.ts:1`, and the same line in each of the demo's 20 `normalization_ast.ts` files), followed by `const normalizationAst: NormalizationAst = {..};` and `export default normalizationAst;`. Deltas: the package is `@isograph/runtime`, because the types and the normalizer do not depend on React and i2 does not name a React-free package after React; the quotes and spacing are `swc_ecma_codegen`'s; the value is the selection array (deltas below).

The alternative is `export default [..] satisfies NormalizationAst;`. `satisfies` checks the value the same way and keeps the value's own literal type as the module's export type, so an importer of the module sees the exact nodes. The annotation was picked because it matches upstream's generated artifacts, and because the artifact's consumers (`entrypoint.ts`, the runtime) only need `NormalizationAst`, not the literal type of one query's AST.

Deltas from upstream (`isograph/libs/isograph-react/src/core/entrypoint.ts:122-159`, `util.ts:10-33`):

- The default export is the selection array. Upstream wraps it as `{ kind: "NormalizationAst", selections }` (`isograph/crates/artifact_content/src/entrypoint_artifact.rs:272-278`), whose `kind` distinguishes it from `NormalizationAstLoader`; i2 has no loader, so nothing reads the wrapper.
- `responseKey` is new on `Scalar` and `Linked`. Upstream recomputes it per node in `getNetworkResponseKey` (`cache.ts:544-558`).
- `isFallible` is dropped. Upstream's normalizer never reads it on a normalization node (`cache.ts` reads only `concreteType`, `fieldName`, `arguments`, `selections`, `type`); pico-runtime.md drops it too. i2 has the data (a selectable's target `Wrapper` contains `Null`), and nothing would read it.
- `concreteType` stays. The normalizer reads it to name a linked record's type (`cache.ts:295-296`, `:322-323`, `astNode.concreteType ?? networkResponseData.__typename`). i2 has the data: `GraphQLEntityData::Object` is concrete, `Interface` and `Union` are abstract (`crates/graphql_network_protocol/src/protocol_data.rs:25-33`). It is `null` exactly when the query selects `__typename` under the field because the target is abstract (query-generation.md, `completed_selection_set` step 1).
- `InlineFragment { type, selections }` is replaced by `Conditional { condition, selections }`. Upstream's `normalizeInlineFragment` (`cache.ts:345-370`) tests `response.__typename === type` and normalizes the selections onto the parent record. `FieldEquals { responseKey: "__typename", value: type }` is that test, named as data.
- `ArgumentValue` has no `Enum` kind, because `MergedValue` has none (query-generation.md), and `Literal`'s value is `number | boolean | null` where upstream's is `any`.
- No `storage` field. pico-runtime.md derives it from an `inline_types` config option that does not exist in i2.

## The condition

```rust
// from crates/isograph_compiler/src/normalization_ast.rs
/// When a conditional node's selections apply to the response object it is evaluated on.
#[derive(Clone, Debug, PartialEq, Eq, PartialOrd, Ord, Hash)]
pub enum NormalizationCondition {
    /// The value under `response_key` in the response object is the string `value`.
    FieldEquals(FieldEqualsCondition),
    /// The operation variable `name` is `value`.
    VariableEquals(VariableEqualsCondition),
}

#[derive(Clone, Debug, PartialEq, Eq, PartialOrd, Ord, Hash)]
pub struct FieldEqualsCondition {
    pub response_key: NormalizationAlias,
    pub value: StringLiteralValue,
}

#[derive(Clone, Debug, PartialEq, Eq, PartialOrd, Ord, Hash)]
pub struct VariableEqualsCondition {
    pub name: VariableName,
    pub value: Boolean,
}
```

`NormalizationAlias` is query-generation.md's (`crates/isograph_compiler/src/merged_selection.rs`); `Boolean` is `isograph_parser::Boolean`. The enum can gain variants.

The condition is protocol-neutral and lives in the core. The query structure keeps the protocol's meaning: the GraphQL `OperationDocument` holds `OperationInlineFragment { type_condition, .. }`, which prints as `... on T`, and an `@include(if: $x)` or `@skip(if: $x)` would print as itself. The protocol derives the AST condition from that structure while building the AST, and the GraphQL protocol supplies `__typename` as the field:

- `... on T` is `FieldEquals { response_key: normalization_alias("__typename"), value: "T" }`, where `normalization_alias("__typename")` is `MergeKey { name: "__typename", arguments: MergedArguments::default() }.normalization_alias()`, the alias the document gives the added `__typename` (`__typename`).
- `@include(if: $x)` is `VariableEquals { name: x, value: True }`; `@skip(if: $x)` is `VariableEquals { name: x, value: False }`. The query structure does not carry these directives yet (open decision 2).

Query text and AST are still produced from one structure, the `OperationDocument`.

### Semantics

- A conditional node writes onto the parent's record. It creates no record and adds no segment to a response key path: its selections read keys of the same response object as the node's siblings, and write fields of the same record.
- `FieldEquals` holds when `response[responseKey] === value`. A key that is absent from the response object, or holds `null` or a value of another type, does not equal `value`; the condition is false and the selections are skipped.
- `VariableEquals` holds when `variables[name] === value`. An absent variable is not equal to either boolean; the condition is false. GraphQL requires `if: Boolean!` on both directives, so an absent variable is a caller error the server also rejects.
- Invariant: a `FieldEquals` field is selected in the same parent selection set, before the conditional node, so a normalizer walking the selection set in order has read it. The generator guarantees this for `__typename`: an inline fragment occurs only under a field whose target is an interface or union (a refinement `asT` is defined only on unions and interfaces, `protocol_data.rs:180-193`; a `Node` fetch wraps in a fragment only when `node` returns an interface or union, entrypoints.md `node_fetch`), and `completed_selection_set` adds `__typename` first under every such target (query-generation.md, step 1). The AST builder checks the invariant anyway (`ConditionFieldNotSelected`, below), because the two facts live in different functions.

### Merging

Two conditional nodes in one selection set with equal conditions are one node whose selections are merged. A conditional node inside another is a nested node; nested conditions are never flattened into a conjunction.

The merge happens before the AST is built. A refinement `asT` is one `MergeKey` (name `asT`, no arguments) in its parent's `MergedSelectionMap`, so every selection of `asT` under one field merges into one entry and one `... on T`. Two distinct refinements of one parent are `asT` and `asU` with `T != U`, so their conditions differ. The `Node` fetch's fragment is the only selection of its selection set besides `__typename` and `id`. The builder therefore never sees two equal conditions in one selection set; it returns `DuplicateCondition` if it does, which no generated document reaches. Under the current grammar no condition nests: `asT` targets an object type, and object types have no refinements.

### Abstract refinement targets

`FieldEquals` on `__typename` cannot express "implements interface `I`": the response's `__typename` is always a concrete object type. That matches i2's refinements. Every `asT` target is an object type:

- `refinement_to` (`crates/graphql_network_protocol/src/protocol_data.rs:210-240`) returns a selectable only for `GraphQLEntityData::Object` (`:216-229`) and `None` for `Interface`, `Union`, `Leaf`, and `InputObject` (`:230-238`). Both callers go through it: `refinement_named` (`:197`) and `graphql_selectables` (`:327-332`).
- On an interface, `refinement_named` additionally requires the target to be an object whose `interfaces` contain the interface (`:182-188`). On a union, it requires membership (`:181`) and then `refinement_to` filters to objects.

Upstream's are concrete too: refinements are created per `concrete_child_entity_name` (`isograph/crates/graphql_network_protocol/src/nested_server_schema/parse_nested_server_schema.rs:362-406`), the subtype map gets interface entries only from object types' `implements` (`:527-532`), and union entries from member types (`:659-665`).

No `... on T` in i2 has an abstract `T`. The `Node` fetch's `... on T` names an object type, because only object types are `Node`-fetched entrypoint parents (entrypoints.md, Which entities may parent an entrypoint).

Later, not v1: abstract refinement targets (interfaces, unions). `FieldEquals` alone cannot express them, because the value the response holds under `__typename` is the concrete type name (`Pet`), never a fixed value that stands for the abstract type. Inside the fragment, the query selects one more aliased field, `... on Named { __refinement__Named: __typename .. }`. The server returns that key only when the object is of the abstract type, so the condition is "the response object has the key `__refinement__Named`": a third variant, `FieldPresent { response_key }`, with no list of concrete types and no subtype check at runtime. The key belongs to the same response object as the fragment's siblings (a fragment adds no path segment), and it is selected inside the fragment rather than before it. The generator owns the `__refinement__` prefix, so the alias cannot collide with a normalization alias: a field name starting with `__` is reserved for introspection (GraphQL spec 3.4.1), and every normalization alias starts with its field name.

### Representation in the artifact

Held: the artifact holds the condition as data (`{ kind: "FieldEquals", responseKey: "__typename", value: "Pet" }`, `{ kind: "VariableEquals", name: "x", value: true }`), and one runtime function evaluates every condition:

```ts
// from libs/isograph-runtime/src/normalize.ts
export function conditionHolds(
  condition: NormalizationCondition,
  response: NetworkResponseObject,
  variables: Variables,
): boolean;
```

Reasons: v1 tests assert facts about artifacts, and data compares (`===` on the fields, structural equality on the object) while functions do not; the artifact stays plain object literals (AGENTS.md, TypeScript: "Generated artifacts are plain object literals and types").

The alternative is a generated function per condition, `condition: (response, variables) => response.__typename === "Pet"`. Its costs: `ArtifactValue` gains a function-expression variant and the SWC printer an arrow-function and expression layer (`===`, member access) that no other artifact needs; a test can only call it on inputs, not compare it; two equal conditions are two distinct function objects, so the runtime cannot key or deduplicate by condition; and the artifact contains code, which the TypeScript section excludes. What it buys is one less `switch` on `kind` per evaluation in the runtime.

## The core AST type

The AST is a core type because both sides of it are generic: the protocol builds it and the host language prints it, and `typescript_artifacts` cannot depend on `graphql_network_protocol` (AGENTS.md: core crates do not depend on it).

```rust
// from crates/isograph_compiler/src/normalization_ast.rs
/// The selections a normalizer walks, in query order. GraphQL rejects an empty selection
/// set, so the protocol never produces one.
#[derive(Clone, Debug, PartialEq, Eq)]
pub struct NormalizationSelectionSet(pub NonEmpty<NormalizationSelection>);

#[derive(Clone, Debug, PartialEq, Eq)]
pub enum NormalizationSelection {
    Scalar(NormalizationScalarField),
    Linked(NormalizationLinkedField),
    Conditional(NormalizationConditional),
}

#[derive(Clone, Debug, PartialEq, Eq)]
pub struct NormalizationScalarField {
    pub response_key: NormalizationAlias,
    pub field_name: SelectableName,
    pub arguments: NormalizationArguments,
}

#[derive(Clone, Debug, PartialEq, Eq)]
pub struct NormalizationLinkedField {
    pub response_key: NormalizationAlias,
    pub field_name: SelectableName,
    pub arguments: NormalizationArguments,
    pub concrete_type: ConcreteType,
    pub selections: NormalizationSelectionSet,
}

/// Whether a linked field's target names the type of every record it links to.
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum ConcreteType {
    Concrete(EntityName),
    /// The record's type is read from the response.
    Abstract,
}

#[derive(Clone, Debug, PartialEq, Eq)]
pub struct NormalizationConditional {
    pub condition: NormalizationCondition,
    pub selections: NormalizationSelectionSet,
}

/// Arguments in `MergedArguments` order: sorted by name, no name twice.
#[derive(Clone, Debug, Default, PartialEq, Eq)]
pub struct NormalizationArguments(pub Vec<NormalizationArgument>);

#[derive(Clone, Debug, PartialEq, Eq)]
pub struct NormalizationArgument {
    pub name: ArgumentName,
    pub value: NormalizationValue,
}

/// `MergedValue` with integers narrowed to GraphQL's 32-bit `Int`.
#[derive(Clone, Debug, PartialEq, Eq)]
pub enum NormalizationValue {
    Variable(VariableName),
    String(StringLiteralValue),
    Integer(i32),
    Boolean(Boolean),
    Null,
    Object(Vec<NormalizationObjectEntry>),
}

#[derive(Clone, Debug, PartialEq, Eq)]
pub struct NormalizationObjectEntry {
    pub name: ValueKeyName,
    pub value: NormalizationValue,
}
```

`isograph_compiler` gains the `nonempty` workspace dependency. `NormalizationArguments` keeps `MergedArguments`' order because the TypeScript `Arguments` is a list, and the store key upstream builds from it (`getParentRecordKey`) depends on its order; sorted arguments give one store key per merge key. An empty `NormalizationArguments` prints as `arguments: null` (upstream `get_serialized_field_arguments`, `isograph/crates/artifact_content/src/generate_artifacts.rs:483-485`).

`Integer(i32)` is narrower than `MergedValue::Integer(i64)` because the TypeScript value is a `number` (`f64`), which represents every `i32` exactly (`f64::from(i32)`), and the workspace denies `cast_precision_loss`. GraphQL `Int` is 32-bit (spec 3.5.1), so a literal outside `i32` is a query the server rejects; the builder returns `IntegerOutOfRange`, which fails the query. The alternative, an `ArtifactValue` integer variant printed from its decimal text that keeps `i64`, is not taken: the server rejects such a query anyway, and a value beyond 2^53 loses precision once the TypeScript source is parsed as a `number`.

    pub name: SelectableName,
    pub arguments: MergedArguments,

/// What a field's target is, which decides whether it has a selection set.

`NormalizationAlias` gains `derive_more::Display` (its text) for the message. `normalization_selection_set` walks the selections in order, keeping the set of response keys and the set of conditions seen so far: a state machine over the selection list whose next step reads what earlier steps produced, so it is a `try_fold` over `(Vec<NormalizationSelection>, BTreeSet<NormalizationAlias>, BTreeSet<NormalizationCondition>)`, then `NonEmpty::from_vec`, which is `Some` because `OperationSelectionSet` is non-empty. `normalization_selection`:

- `InlineFragment`: `Conditional { condition: inline_fragment_condition(type_condition), selections }`. A `FieldEquals` whose `response_key` is not in `preceding` is `ConditionFieldNotSelected`; a condition already seen is `DuplicateCondition`.

## Later / open area: objects without an identity field

This is not a v1 change and has no held option. It is an optimization that does not matter for v1, and an open area of thinking.

What v1 does, upstream's behavior: a linked field whose target has no identity field (a `date` object with `day`, `hour`, `minute`) is a `Linked` node whose `selections` list every subfield, like any other linked field. The normalizer writes it as its own record, whose identity is derived from the parent record, the field name, and the arguments (`getDataIdOfNetworkResponse`, `isograph/libs/isograph-react/src/core/cache.ts:599-642`: `<parent typename>:<parent id>.<fieldName>`, then `.<index>` in a list, then one chunk per argument). The parent record holds a link to that record.

The open idea: such an object has no identity of its own, so the normalizer could merge it directly into the parent record, possibly deeply (a `date` inside a `schedule` inside a `Pet`, all stored on `Pet`'s record). The normalization AST then might not need to list the object's subfields: the normalizer would copy the response object's value under the parent's `responseKey` without walking it.

Open question: an object with an identity field nested inside an identity-less object (`Pet.schedule { date { .. } owner { id .. } }`, where `schedule` has no identity and `owner` has `id`). Copying `schedule` without walking it would store `owner` inside `Pet`'s record instead of as its own record, so updates to that `Owner` elsewhere would not reach it. The AST would have to list the subfields down to every object with an identity field. The user's intuition is that this shape looks like a schema bug, but it is a common GraphQL pattern. The identity-less object's identity might then have to come from its relationship with the parent, as Relay derives a client id from the parent record and the field path, rather than the object being merged into the parent record.

## Open decisions

### 1. Where GraphQL-specific names live

Upstream hardcodes `__typename`, `id`, `InlineFragment`, and `concreteType` in its core (`NormalizationKey::Discriminator`, `NormalizationKey::Id`, `MergedServerSelection::InlineFragment`, `ConcreteTargetEntityName` in `isograph/crates/isograph_schema/src/create_merged_selection_set.rs:33`, `:76-82`, `:134-138`, `:170-184`; the `__typename` and `id` insertion at `:1414-1463`; the text and AST printers in `artifact_content`) and in its runtime (`cache.ts:296`, `:356`).

Settled by the condition design: the AST's condition is protocol-neutral and lives in the core (`NormalizationCondition`), the AST node kinds are core types, and the protocol maps its own constructs (`... on T`, `@include`, `@skip`) to conditions. `concreteType` is a core field whose value the protocol decides.

Open: where the merged selection structure's discriminator and identity fields, and its conditional selections, live.

- (A) query-generation.md as written. The core's `MergedSelectionMap` (`crates/isograph_compiler/src/merged_selection.rs`) has one node kind, `MergedSelection { selectable, target, selection_set }`, with scalar, linked, and refinement encoded in the protocol's opaque `SelectableData` and `EntityData`. The GraphQL protocol adds `id`, `__typename`, the `node` field, and inline fragments while building its `OperationDocument` (`completed_selection_set` and `operation_document`, `crates/graphql_network_protocol/src/operation_document.rs`), prints the text from it, and builds the AST from it (this doc). The core owns the normalization alias format. Costs: each protocol writes its own AST builder and its own completion; the invariants that link completion and AST (`__typename` precedes a condition, conditions unique) are checked across two protocol functions and surface as `ConditionFieldNotSelected` and `DuplicateCondition`. Changes: none beyond this doc; it is what is being implemented.
- (B) The core owns a protocol-neutral merged structure with variants for the discriminator, the identity field, and a conditional selection (`MergedSelection::Field`, `::Discriminator`, `::Identity`, `::Conditional(NormalizationCondition, MergedSelectionMap)`), and inserts the discriminator and identity itself from facts the protocol reports. `NetworkProtocol` supplies the names (`__typename`, `id`) and the facts (whether an entity is abstract, its identity field, how a refinement selectable becomes a condition), and prints both the query text and the AST from that structure. Changes: query-generation.md changes 6 and 7 are rewritten while they are being implemented: the map type gains variants, `completed_selection_set`'s steps 1, 2, and 5 move into the core's merge, `NetworkProtocol` gains methods for the names and facts, and `OperationDocument` becomes a GraphQL view of the core structure or is removed. Costs: a second protocol gets discriminator, identity, and conditions without writing completion; the core's map carries variants that a protocol without a discriminator never produces; more trait surface on `NetworkProtocol`; a redesign of work in progress.
- (B') As (B), with the AST built once in the core from the neutral structure instead of by the protocol. Changes: `normalization_ast` moves to `isograph_compiler`; `QueryArtifact` loses `normalization_ast` and `query_for_entrypoint` builds it beside the protocol's text.
